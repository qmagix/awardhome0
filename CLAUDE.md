# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AwardHome — "digital trophy case" for competitive dance: ~900k awards scraped/imported from 14+ competitions, served as public dancer/studio/org pages plus claim-and-manage dashboards.

## Commands

- `npm run dev` — run with auto-restart (`node --watch server.js`). Plain `npm start` does NOT reload: EJS views are re-read per render, but route/JS changes need a restart — a classic trap where a new view renders but its new endpoint 404s.
- `npm test` — HTTP smoke suite (`test/smoke.js`), the only test suite. Boots against the local DB; expects real seed data (e.g. studio 1, dancer profiles).
- `node database.js` — apply schema/migrations (idempotent; also run by deploy).
- `npm run gate` — pre-deploy gate (run before EVERY deploy): smoke suite + mobile API contract test (`test/api_mobile.js`, own throwaway DB copy) + adversarial-DB page sweep (`scripts/sweep_public_pages.js`, worst-case data states: approved coins/acks/photos, corrupt custom_icons) + authenticated route audit (`scripts/audit_get_routes.js`). Catches the "rare data state × shared render path" 500 class that single-entity checks miss. Prod also runs an hourly sentinel (`utils/sentinel.js`, `ENABLE_SENTINEL=true`) probing stratum-sampled real pages, alerting reviewers + Sentry.
- Deploy: `npm run gate` → commit → push to origin main → `ssh -i deploy/awardhome-key.pem ubuntu@34.197.219.72 /opt/awardhome/deploy/deploy.sh` (pull → npm ci → migrate → restart → healthz). Prod has live user data — never copy a local DB over it; achieve data parity by running the same import scripts on both sides (see `docs/db_operations.md`, memory notes).
- Data scripts: `node scripts/<name>.js`, run from repo root. Data dirs (`raw/`, `tobeprocessed/`) live at repo root; scripts must anchor paths with `path.join(__dirname, '..')`.
- Manual QA on prod: `node scripts/qa_fixtures.js seed|remove|status` — transient "(please ignore)" test tenant (org/studio/dancers/awards), no is_test filters by design; register walkthrough accounts as `qa-*@awardhome.com` so `remove` finds them; never leave seeded overnight (3:30am featured cron).

## Architecture

Express 4 + EJS + SQLite (no build step, no ORM, no client framework).

**Database** (`database.js`): one shared connection per process (cached promise), WAL + busy_timeout. `process.env.DB_PATH` overrides the file — this is how the staged import and throwaway test copies work. Schema = `CREATE TABLE IF NOT EXISTS` block + try/catch `ALTER TABLE` migrations in `initDb()`, which runs only via `node database.js` (not on server boot); some admin routes defensively `CREATE TABLE IF NOT EXISTS` so new tables work before a migrate. Foreign keys are intentionally OFF (legacy orphans — see `docs/db_operations.md`).

**Middleware order in `server.js` matters**: helmet → body parsers → **`/api/v1/mobile` (bearer-only; deliberately before session/CSRF/beta — see Mobile API below)** → session (SQLite store) → `res.locals.user` → CSRF (global; token from `_csrf` field, `?_csrf=` for multipart since multer parses after, or `X-CSRF-Token` header auto-added to fetch by `public/js/csrf.js` + meta tag in `partials/header.ejs`) → beta gate on `/dance` + `/dancer` (`BETA_MODE`/`BETA_ACCESS_KEY` in .env; unlock via `?beta=KEY`) → routers (`routes/auth`, `routes/dance/*`, `routes/admin`, `routes/feedback`).

**Auth/roles** (`middleware/auth.js`): roles `user`/`studio_owner`/`dancer_owner`/`org_owner`/`admin`/`superadmin`, but ownership checks use `owner_id` columns, not roles. `requireOrgOwner({ allowAdmin: false })` keeps plain admins out of owner+superadmin surfaces (branding, marketing). Many admin tools are superadmin-only.

**Data pipeline** (the real complexity): scrapers in `scripts/` cache HTML under `raw/<org>/<year>/` (fetch bookkeeping in the `scrape_log` table drives incremental refetch); PDF orgs are download-only pending manual QA (`tobeprocessed/pdf/`); txt-flow orgs (Ultra, Refresh) scrape → reviewable txt → idempotent import via `scripts/update_txt_org.js`. The Monday cron runs `scripts/weekly_update.js` **staged**: snapshot live DB → run full pipeline against `staging_import.sqlite` (via `DB_PATH`) → `scripts/validate_import.js` scores the delta against each org's own history → green auto-promotes (deterministic cache replay against live), amber/red holds with `reports/PENDING_REVIEW.json` + email; review at `/admin/import-review`.

**Family submissions** (`utils/submissionsDb.js` + `utils/submissions.js`): family-entered awards stage in a **separate SQLite file** (`submissions.sqlite`, `SUBMISSIONS_DB_PATH` override) so a submission spike never contends with the serving DB; schema applies on first connection, not via `node database.js`. Nothing canonical is written — promotion is a later milestone. Rules live in the service, not the router, so the web form and the future mobile API can't drift: studio is derived from `dancer_studios` (never typed), group size is required (it decides the solo-vs-junction write path), text is re-normalised server-side, writes are idempotent on `(user_id, client_submission_id)`, and per-household daily limits are logged append-only. `award_provenance` stays in the canonical DB — promotion writes it in the same transaction as the award. Behind the `family_submissions` flag. See `docs/mobile_app_development_plan.md`.

**Promotion** (`utils/promotion.js`) is the ONLY door from staging to canonical, and runs behind a reviewer (`/manage/studio/:id/submissions`, studio owner). Five rules: the declared **group size** picks the write path (solo double-writes `awards.dancer_id` + junction, group = junction only; unknown is treated as a group); **find before create** on (event, studio, routine key, place, category, award type) — mandated ETL idempotency, and what makes the two-file write retry-safe; **tombstones are never resurrected** (`award_dancer_removals` → refuse, don't silently skip); **no canonical award without a canonical event** (a submission on an unpromoted candidate can't promote); **typed cast names never become dancer profiles**. `award_provenance` is written in the same transaction. Scope is enforced twice (owner-of-studio, then submission-belongs-to-studio) and answers 404 so probing ids reveals nothing.

**Offline outbox** (`mobile/src/outbox/`, M7): `client_submission_id` is minted when a draft is CREATED and never regenerated — the client's promise is "always the same id for the same draft", not "send once", which is what makes exactly-once achievable over a venue's wifi given the server's idempotency. A draft may be sent many times; that is fine. Drafts that exhaust retries are PARKED, never discarded. Storage is `expo-sqlite` (not AsyncStorage — a full-file JSON rewrite loses everything on a partial write). Event sessions are SERVER-issued get-or-create so a reinstall rejoins the weekend; another household's session id is dropped, not rejected. Picking an event needs signal once per weekend; everything after is offline. Card photo/note ride on the submission and are copied to `award_card_photos`/`award_acknowledgements` at `pending` by promotion — submitting publishes nothing. Push (`utils/push.js`) is decisions-and-questions only, gated on `ENABLE_PUSH`.

**Mobile app** (`mobile/`, M6): Expo SDK **54** / RN 0.81 / TS **strict** — pinned to whatever the developer's App Store Expo Go reports as its supported SDK, NOT npm-latest (57). App Store Expo Go is capped by the phone's iOS, so re-downloading never fixes a version mismatch; only changing the project's SDK does. `npm run web` renders the app in a browser and never has this problem. `expo-doctor` must stay 18/18. Expo Router typed routes. `src/api/schema.ts` is GENERATED from `docs/openapi_mobile.json` (`npm run api:types`) — never hand-edit it, and never restate a response shape by hand. `src/api/tokens.ts` deliberately imports nothing from React Native (fetch + storage are injected) so the token lifecycle is testable in plain Node; its load-bearing property is **single-flight refresh** — the server revokes a session on a replayed refresh token, so two parallel refreshes sign the user out. Refresh token in `expo-secure-store`, access token **memory only**. Checks are `npm run mobile:check` and are deliberately NOT in `npm run gate` (prod has no `mobile/node_modules`). Universal links: `routes/wellknown.js` serves the association files from env vars and **404s until configured** — a placeholder is worse than nothing because the platforms cache them. Nothing in the app has been run on a device.

**Mobile API** (`routes/api/mobile.js`, `utils/mobileAuth.js`): `/api/v1/mobile` is mounted in `server.js` **after `express.json()` and before the session store, CSRF, and the beta gate** — the only place router order carries a security argument. Bearer tokens are not ambient, so CSRF does not apply (it isn't being skipped), and mounting before session means the API never issues a cookie — asserted by `test/api_mobile.js`. Only token *hashes* are stored; refresh tokens rotate every use and a replayed one revokes the session. Guest reads work with no token where the web equivalent is public. Writes call the same M1–M4 services as the web, so the two clients can't drift. Evidence (`utils/evidence.js`) is magic-byte sniffed, EXIF-stripped, written 0600 **outside `public/`**, and served only to uploader + reviewers; the storage driver is pluggable because the S3-vs-R2 decision is still open, and malware scanning is a hook (`scan_status` stays `pending`), not an implementation. Contract at `/api/v1/mobile/openapi.json` (`docs/openapi_mobile.json`). `npm run test:api` is gate stage 2 and runs against its own throwaway DB copy.

**Convergence** (`utils/convergence.js`): two households describing one win reach ONE award with two links. Placement and text keys are normalised ("1st"/"1"/"First" fold), and **absence is not disagreement** — a blank field matches and is then enriched, while two different filled values keep the awards apart (so "1st in Teen Contemporary" and "Overall High Score" on one routine stay distinct). Enrichment never overwrites existing values. **Corroboration**: unrelated households (different account AND different dancer) promote each other at `corroborated`, no reviewer. **Independents** (no director to ask) **curate privately by default** — family entries stay in staging until either corroboration (still automatic, still no AwardHome involvement) or a superadmin `independent_publish_status` grant, which is retroactive over the whole record; revoking is not. Published independents sit at `family_submitted` and are held out of every ranking by `rankableAwardSql()` until corroborated. A missing `studio_id` is a data gap, never independence. **Contested dancer claims** mark both sides `contested`, which removes them from the studio queue by construction (studio routes filter `pending`) and leaves them to `/admin/claims`. `/admin/submissions` catches everything no studio owner would ever see — above all submissions for dancers at **unclaimed** studios, which would otherwise rot. `award_corrections` are field-level proposals; accepting applies the field and writes provenance in one transaction. `scripts/archive_metrics.js` (design §14) runs at the end of each weekly import; its duplicate metrics are calibrated against the real corpus — don't loosen the keys without re-measuring.

**Card photo approval is delegated to studios** (`utils/cardPhotos.js`), not superadmin: upload → visible only to families of dancers *on that award* → one objection from a cast family blocks studio approval and routes to AwardHome (reuses `content_flags`; only households owning a claimed dancer in the routine may object) → otherwise the studio publishes from Pending Verifications → public reports keep the existing one-report-darks + reinstate guard. Consent at the studio step is **passive** on purpose: a unanimity rule would never fire, since most dancers on a big group have no claimed profile. Dancer-level default photos (`dancers.card_photo_*`) still go through superadmin — no routine, so no cast to consult.

**Event candidates** (`utils/eventCandidates.js` + `utils/eventPicker.js`): families may create an event but only ever as an `event_candidates` row in the staging DB — **no canonical `events` row is ever written by a family action** (smoke-enforced). The picker ranks three sources: geocoded `org_upcoming_events` (the only one that can answer "am I here today?" — canonical `events` have no geo and a free-text `date_string`), other families' candidates, then canonical events by name. Dedup runs server-side *before* a create is accepted; both rows share a `dedup_cluster_id` when two families insist. Two promotion paths, both idempotent because they span two SQLite files and cannot share a transaction: superadmin at `/admin/event-candidates`, or `scripts/merge_event_candidates.js` auto-merging an unambiguous match after the organizer's own import (runs at the end of each successful weekly update). Ambiguity is never guessed — two plausible events is a tour with two nearby stops.

**Crons** live in `server.js` via node-cron (not system crontab): nightly backups (`ENABLE_NIGHTLY_BACKUPS`), nightly featured-studio rotation, weekly orphan check, Monday weekly scrape (`ENABLE_WEEKLY_SCRAPE`, prod only). Litestream→S3 is the authoritative prod backup.

**Award card design system**: `.flip-card` is `container-type: inline-size`; ALL internal card sizes use `cqw` units calibrated to design widths (portrait 300px → 1cqw = 3px; landscape 460px), so cards zoom like images; a rem/px fallback outside `@supports` serves old browsers. New card elements must follow this pattern or they won't scale. Per-org branding settings live in `organizations.custom_icons` (JSON) and reach cards as CSS custom properties set inline by `views/partials/dancer_award_card.ejs`.

**Caching** (`utils/cache.js`): in-memory stale-while-revalidate. Expired hits return stale data and refresh in background — no visitor ever waits. Use `refresh(key)` (background swap) rather than `invalidate(key)` (hard delete → next visitor pays the recompute) unless staleness is unacceptable. Homepage data (`dance-home`) is warmed at boot in `routes/dance/public.js`.

**Email** (`utils/mailer.js`): Gmail or Resend via `EMAIL_PROVIDER`. Outreach invites (`utils/invites.js`) honor the `email_suppressions` unsubscribe list and HMAC unsubscribe links; studio invites are one-shot templated, organizer letters are hand-composed with a `{CLAIM_LINK}` placeholder that becomes a single-use 30-day org-claim token at send time.

## Deliberate product decisions (don't "fix")

- **No public claim button on organization pages** — an unclaimed state would advertise which orgs aren't partnered yet. Orgs claim only via private links in invitation emails (`/claim/org/:token`).
- **Homepage org cards don't link to org pages** (decided 2026-08-24) — org data stays low-profile until the org partners; the org page itself stays public (it's the demo link in invitation letters). Cards instead record clicks (`POST /api/org-card-click` → `org_card_clicks`, impressions in `daily_counters`) as demand evidence for outreach — CTR shows on `/admin/orgs`. Cards must stay free of any claimed/unclaimed signal. The admin homepage (`index_admin.ejs`) keeps its links.
- **Org logos on cards are approval-gated, default OFF** — a superadmin hand-fits each logo into the fixed circular "coin" (position/rotation sliders are superadmin-only on `/manage/org/:id/branding`) and ticks "Approved for public display". Owners get size/opacity only; the concierge step is part of the pitch.
- Marketing language: "your brand on every card dancers share."
- **Public studio URLs use `studios.unique_id`** (`STU-<hex>-slug`), never the numeric id — numeric `/dance/studio/62`-style URLs deliberately 404 with NO redirect (a redirect would be an enumeration oracle for scraping the whole dataset). Manage/admin routes stay numeric (auth-gated). Same pattern as dancer `unique_id` URLs.
- **Independent dancers get a synthetic one-dancer studio** (`studios.is_independent = 1`, name carries the dancer's `unique_id`) rather than sharing a regional "Independent" roster — a shared roster lets `auto_merge_dancer_profiles` fuse two same-name children. This makes "independent" a data case, not a code case, so every resolver keeps working on a studio key. Two invariants: names stay globally unique (`merge_studio_aliases` skips independents), and every studio-facing surface excludes them (directory, search, featured, rankings, homepage count, merge suggestions; the studio URL redirects to the dancer). Cards render `Independent` via `studioDisplayNameSql()`. Detection is a **reviewed per-org list** in `utils/independents.js` — never a regex on `independ`, because `IndepenDANCE Studio` is a real studio. Migration: `scripts/migrate_independent_studios.js`.
- Self-reported studio data enters as `is_self_added = 1, verification_status = 'unverified'`; scraped events are matched by `name + year + org_id`.

## Data-model and coding rules (imported from GEMINI.md)

- **Junction tables, not legacy columns**: dancers↔awards go through `award_dancers`, dancers↔studios through `dancer_studios`. Never map group awards via the legacy 1:1 `awards.dancer_id` column.
- **Pseudo-studios for collaborations**: a cross-studio win ("Studio A & Studio B") keeps the concatenated string as its own studio row — no studio pivot table. Dancers bridge the affiliations via `dancer_studios`.
- **Scraper/ETL idempotency is mandatory**: check for existing records (event name, performance name, place, category) before inserting; use transactions for batches. The weekly staged-import validator scores idempotency breaks as failures.
- **Vanilla CSS/JS only** — no TailwindCSS or other frameworks without explicit permission. Scraping uses Cheerio + Axios (Puppeteer for dynamic sites).

## Workflow conventions (imported from GEMINI.md)

- **Commit without being asked** after each verified feature or bug fix (code must run clean first). Pushing and deploying still require an explicit request.
- **Documentation parity**: when a user-facing workflow or UI tool changes, proactively update the relevant FAQ view (`views/faq_admin.ejs`, `views/faq_dancer.ejs`, `views/faq_organizer.ejs`) in the same change.
- **Living docs to maintain**: `features.md` (feature documentation), `user_manual.md`, `TODOS_and_DONE.md` (running to-do list), `ideas.md` (novel/patentable product ideas as they come up in brainstorms). Docs belong at the root or `./docs`.
- `user_prompts.md` and `interaction_history.md` are artifacts of the previous Gemini workflow — do not maintain them going forward.
